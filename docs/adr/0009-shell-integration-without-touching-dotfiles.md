# ADR-0009 — Shell integration is loaded by Nymbra, never by editing your dotfiles

**Status:** Accepted · 2026-10-18

## Context

`OSC 133` is a cooperative protocol. A terminal cannot tell a prompt from a
command's output by looking at the bytes: a prompt, a command, and the text a
command printed are the same stream coming back up the pty. Only the shell knows
where one ends and the next begins, so the shell has to be taught to say so — and
that teaching has to happen from inside the shell's own startup.

The way every terminal solves this is the same: **write a line into the user's
startup file.** iTerm2 offers a menu item that does it for you; kitty, WezTerm and
Ghostty ship a snippet and document the `source` line to add by hand.

That is a reasonable trade for a terminal whose user chose it and knows what a
shell startup file is. It is the wrong trade for this one.

- **The promise in the settings window is a checkbox.** "Turn on shell
  integration" that answers with "now paste this into your `.zshrc` and open a new
  tab" is not the feature that was promised, and a beginner has no way to tell a
  correct paste from a broken one.
- **A terminal that rewrites dotfiles is a terminal you cannot uninstall.** A line
  appended to `.zshrc` outlives the app. If the directory it sources is later
  deleted — by an uninstall, a clean-up, a migration — the user's shell prints an
  error they did not cause and cannot place, on every new shell, for good.
- **The user's dotfiles are theirs.** They may be symlinked into a dotfiles
  repository, generated by a manager, reviewed in a diff, or shared with the
  dozens of other machines they log in to. A terminal has no business in there.
- **The snippet is the one piece of Nymbra that runs inside somebody else's
  program.** A bug in it does not degrade a window; it breaks every shell the user
  opens. That argues for a mechanism that can be switched off completely, not one
  that leaves edits behind.

## Decision

**Nymbra never writes to the user's startup files. It loads the integration
itself, by pointing `ZDOTDIR` at a directory of its own.**

zsh reads its startup files from `$ZDOTDIR`, falling back to `$HOME`. Nymbra
starts a *login* shell — `zsh -l`, so all four files that a login interactive zsh
reads are in play, plus `.zlogout` on exit — and gives it:

- `ZDOTDIR` = `~/Library/Application Support/Nymbra/shell/`, written fresh on
  every launch;
- `NYMBRA_USER_ZDOTDIR` = wherever the user's own startup really lives.

The generated directory contains every file zsh asks for by name — `.zshenv`,
`.zprofile`, `.zshrc`, `.zlogin`, `.zlogout` — each of which sources the user's
own file first and then, in `.zshrc`, the snippet:

```zsh
# Generated by Nymbra on every launch; edits here are overwritten.
[[ -r "${NYMBRA_USER_ZDOTDIR:-$HOME}/.zshrc" ]] && source "${NYMBRA_USER_ZDOTDIR:-$HOME}/.zshrc"

source "${ZDOTDIR}/nymbra.zsh"
```

Four parts of that are load-bearing.

1. **Every file is generated, the empty ones included.** zsh asks for these files
   *by name*. A name left out of the directory is not "a file zsh skips" — it is
   one of the user's own files that never runs, because `ZDOTDIR` moved.
   Generating all five is what keeps a `.zprofile` that sets `PATH` working, and it
   is the difference between "this works for most people" and "this works".
2. **`ZDOTDIR` is set in the environment of one child process.** It is written
   nowhere, exported to nothing, and invisible to every other terminal. The blast
   radius of the mechanism is the single shell it was used to start.
3. **Turning the setting off stops pointing at the files.** There is nothing to
   undo, because nothing outside `Application Support` was ever changed. Delete
   Nymbra and the shell is exactly as it was.
4. **The snippet changes nothing the user can see.** It does not define, wrap or
   extend `PS1`. A prompt built by `precmd`, by `PROMPT_SUBST`, or by a framework
   stays byte-for-byte what it was. `B` is a mark *about* a prompt, not a change
   to one.

**zsh only, so far.** A login bash reads `.bash_profile` and never `.bashrc`, so
the same trick needs a different file and a different hook — and an integration
that half works is worse than one that plainly does not exist yet.
`ShellIntegration.supports(shell:)` says no rather than doing something
surprising.

**`B` is not sent yet.** `A` (a prompt is coming), `C` (a command is about to run)
and `D` (it finished, with its status) are enough for everything M4 promises. `B`
marks where the command line begins, and the only way to know when zsh has
finished *drawing* its prompt is to define its `zle-line-init` widget — the line
editor, the one part of a shell where being second in line is worse than not
being there at all.

**Off by default.** `behaviour.shellIntegration` starts as `false`. This changes
how somebody's shell starts, and a terminal that quietly rearranges your startup
is not one to trust.

## Consequences

- **Only a real shell can be believed.** `--shell-integration-test` starts an
  actual zsh behind a temporary stand-in for the user's config, and requires both
  halves: that the marks arrive, *and* that the stand-in still ran. Because the
  snippet is sourced from the generated `.zshrc`, the marks arriving is also proof
  that file did its job.

  Asserting against bytes we wrote ourselves would have passed while sending
  nothing, and did. Two bugs here were invisible to everything except a live
  shell:

  1. **`local status=$?` — `status` is a read-only special variable in zsh** (a
     synonym for `$?`), so the assignment aborted `precmd` on its first line and
     not one mark was sent. zsh printed the prompt anyway; a test that only asked
     for a prompt would have passed.
  2. **`add-zsh-hook zle_line_init …` — `add-zsh-hook` does not accept that
     hook.** Its hooks are `chpwd`, `precmd`, `preexec`, `periodic`,
     `zshaddhistory`, `zshexit` and `zsh_directory_name`. The `|| true` beside it
     swallowed the failure silently. The thing that does exist is a `zle` widget,
     which is why `B` waits.

- **A failing command is reported as failing.** The test runs `(exit 7)` and
  requires the terminal to see `commandFinished(7)`, not merely that something
  finished. A terminal that reported success regardless would pass any weaker
  check — and a green badge on a failed build is precisely the lie M4 exists to
  prevent.

- **A generated startup file is allowed to end with a non-zero status.** When the
  user has no `.zshrc`, the generated one ends with the status of a failed
  `[[ -r … ]]`. That is fine, and it was **measured rather than assumed**: zsh
  does not look at the status of a startup file, under `err_return` or under
  `set -e`. It was tempting to "fix" with an `if`, and the assumption behind the
  fix was wrong. (The same experiment found something worth knowing anyway: with
  `set -e`, a failing command exits the shell, so no exit status is ever
  reported. That is the shell being right, and it is why the test does not assert
  a status in that case.)

- **Failing to write the files is not an error the user sees.** A terminal that
  refused to open a window because it could not write its own shell helper would
  be a worse bug than the one it was reporting. The shell starts without
  integration — the same visible result as the setting being off.

- **It lands on the next shell, not the running one.** `ZDOTDIR` is part of the
  environment a shell is born with, and an environment cannot be handed to a
  process that has already started. The setting is therefore read once per spawn
  rather than remembered on a tab, where it would be stale the moment it was used.

- **Known limitation: a user who sets `$ZDOTDIR` themselves gets a quiet no-op.**
  Their `.zshenv` runs — ours sources it first — it re-points `ZDOTDIR`, and zsh
  then reads *their* `.zprofile` and `.zshrc` from the new location, so the
  generated `.zshrc` that sources the snippet is never reached. Nothing breaks;
  the integration simply does not appear. The fix is to source the snippet from
  the generated `.zshenv` as well, guarded so the hooks install exactly once,
  since `.zshenv` runs before the variable can be changed.

- **Alternatives rejected.**
  - *Append a `source` line to the user's `.zshrc`, or ask them to.* See Context:
    it outlives the app, it fails in the user's face, and it is not the feature
    that was promised.
  - *Override `PS1`/`PROMPT` to emit the marks.* It changes what the user sees,
    and it cannot survive `PROMPT_SUBST` or a prompt framework that assigns
    `PS1` after us.
  - *Start the shell as `zsh -c 'source …; exec zsh'`.* The extra process layer
    makes job control and Ctrl+D subtly wrong, and the shell that ends up running
    is one Nymbra built rather than the one the user configured. `ZDOTDIR` is the
    hook zsh provides for exactly this purpose, so there is no reason to reach for
    anything cleverer.
